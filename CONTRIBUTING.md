# Contributing to jax-healpy

Bug reports, fixes, new functions and improvements of the documentation are welcome. This page
describes how the repository is organized. The conventions that the maintainers and the coding
agents follow are detailed in
[AGENTS.md](https://github.com/CMBSciPol/jax-healpy/blob/main/AGENTS.md).

## Reporting a bug

Open an [issue](https://github.com/CMBSciPol/jax-healpy/issues) with a minimal example that
reproduces the bug, the result you expected, and the one you got, with the full traceback. When
the result disagrees with healpy, give the healpy call you compare with. Add the versions and the
devices that this command prints:

```bash
python -c "import importlib.metadata as m, jax; print('jax-healpy', m.version('jax-healpy')); jax.print_environment_info()"
```

## Development environment

Clone the repository, create the environment with [uv](https://docs.astral.sh/uv/), and install
the git hooks:

```bash
git clone https://github.com/CMBSciPol/jax-healpy.git
cd jax-healpy
uv sync --all-extras  # add --group cuda for NVIDIA GPUs, with CUDA 13
uv run prek install
```

The environment holds the `dev` group, with the tools of the tests, of the documentation and of
the hooks. `--all-extras` adds ducc0 and s2fft, the libraries of the spherical harmonic
transforms. s2fft is installed from its GitHub repository: its latest release computes wrong
polarized transforms on HEALPix maps.

The hooks run at each commit on the staged files, with [prek](https://github.com/j178/prek):
ruff, also on the notebooks, pycln, bandit, zizmor on the workflows, the stripping of the
outputs of the notebooks and the check of `uv.lock`. The CI runs the same hooks on the whole
tree:

```bash
uv run prek run              # the staged files, as the commit hook
uv run prek run --all-files  # the whole tree, as the CI
```

A file that git does not know is checked by nothing: `git add` it first, by path. Fix what the
hooks report rather than committing with `--no-verify`.

## Tests

```bash
uv run pytest                                  # the whole suite
uv run pytest -n auto                          # in parallel, as the CI
uv run pytest tests/pixelfunc/test_ang_pix.py  # a single file
uv run pytest -m slow                          # only the slow tests
```

The suite runs the tests under `tests/` and executes the notebooks of the user guide. The tests
marked `slow` are deselected by default, and the CI does not run them. The CI runs the suite on
Python 3.11 to 3.13 with the oldest supported version of JAX, and on Python 3.14 with the latest
one, with and without s2fft. On a pull request whose changed files cannot affect the tests, such
as `README.md` or the Markdown pages of the documentation, the test jobs skip their steps: the
files are listed in the `changes` job of `.github/workflows/ci.yml`.

Most of the time of the tests goes to the compilation of the JAX programs, and the tests drop the
programs compiled by a module once it is done, to bound their memory. A persistent compilation
cache, which the CI keeps between its runs, spares the compilations from one run to the next:

```bash
export JAX_COMPILATION_CACHE_DIR=~/.cache/jax-healpy-tests
export JAX_PERSISTENT_CACHE_MIN_COMPILE_TIME_SECS=0
uv run pytest -n auto
```

A test compares the result with healpy or with an analytical value. A function that is meant to
be compiled, batched or differentiated is also tested under `jax.jit`, `jax.vmap` or `jax.grad`,
and under both precisions, with the `x64` fixture, when the 32-bit and the 64-bit behaviors
differ. Patches use the `mocker` fixture of pytest-mock.

## Documentation

The site is built with [Zensical](https://zensical.org). The pages of the user guide are
Jupyter notebooks under `docs/user-guide/`, committed without their outputs: `docs/build.sh`
executes them and converts them to Markdown before building the site. The API reference is
generated by mkdocstrings from the docstrings, in the NumPy style.

```bash
uv run --group docs --extra cpu sh docs/build.sh  # build the site into site/
uv run zensical serve                             # live preview, after a first build
```

Read the Docs also builds the site of each pull request: the link is in its checks.

## Pull requests

- A change that needs a decision is discussed in an issue first: a new dependency, a change of
  a public signature, a departure from healpy, a break of compatibility.
- Name the branch `<type>/<description>`, in the style of
  [conventionalbranch.org](https://conventionalbranch.org): `fix/alm2map-lmax`,
  `docs/polarization-page`.
- A pull request carries one change, in a single commit. Its message follows
  [Conventional Commits](https://www.conventionalcommits.org), with a subject under 72
  characters, such as `fix(sphtfunc): infer lmax from the size of the alms`, and the pull
  request takes it as its title. Each revision amends the commit and is pushed with
  `git push --force-with-lease`.
- A fix comes with a test that fails without it. A performance claim comes with the timings
  before and after the change, and how they were taken.
- The pull request updates the documentation that the change makes untrue. A change that the
  users can observe gets an entry under `[Unreleased]` in
  [`docs/changelog.md`](https://github.com/CMBSciPol/jax-healpy/blob/main/docs/changelog.md),
  ending with the number of the pull request, as in `(#54)`.
- The description links the issue that the pull request closes (`Closes #<number>`), and says
  what was run to check the change, and what was not.

## Releasing

The changes of a release are dated in the changelog before the release is tagged, in a pull
request `chore: release vX.Y.Z` that only changes `docs/changelog.md`:

- the changes listed under `[Unreleased]` move to a section `## [X.Y.Z] - YYYY-MM-DD`, under an
  empty `## [Unreleased]` section;
- at the bottom of the file, the link of `[unreleased]` compares `vX.Y.Z` with `HEAD`, and a new
  link `[X.Y.Z]` compares the previous tag with `vX.Y.Z`.

Once the pull request is merged, create the release `vX.Y.Z` on GitHub, with a new tag on
`main`. The `Release to PyPI` workflow publishes the package to PyPI. It fails, and publishes
nothing, if the changelog of the tag has no section for the version.

If the release is created before the changelog is dated, the workflow fails and publishes
nothing, but the release and its tag exist. Delete them, date the changelog, then create the
release again, with the same version:

```bash
gh release delete vX.Y.Z --cleanup-tag --yes
git tag -d vX.Y.Z  # if the tag was fetched
```
